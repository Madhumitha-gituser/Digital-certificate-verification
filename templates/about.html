1. SHA-256 Hashing: The Unique Fingerprint

SHA-256 (Secure Hash Algorithm 256-bit) computes a fixed 256-bit (64 hex character) digest of arbitrary input data. Due to the avalanche effect, any alteration to the certificate details produces an entirely different hash.

Input: "Ananya Sharma"
Hash: 3f2a9b1c...
Input: "Fake Student" (altered)
Hash: d8e4f72a... (completely different)
Key Property: SHA-256 is a one-way cryptographic hash function: you cannot reconstruct the original certificate data from the hash alone.
2. Canonical JSON: Deterministic Formatting

Standard JSON serialization is arbitrary with regards to key order and whitespace. If a signer serializes {"name":"Ananya","id":"001"} and the verifier serializes {"id":"001","name":"Ananya"}, their byte hashes will differ.

# Deterministic canonical formatting json.dumps(cert_data, sort_keys=True, separators=(',', ':')) # Canonical output (guaranteed identical byte sequence): {"cert_id":"CERT-2026-001","course":"B.E. Information Science...","institution":"Demo Engineering College","issue_date":"01 October 2026","student_name":"Ananya Sharma"}
Both the signing and verification routines use the exact same canonical serialization algorithm.
3. RSA-2048 Digital Signatures with PSS Padding

Digital signatures rely on asymmetric public-key cryptography:

  • Private Key: Kept strictly secret on the issuing server. Signs the canonical certificate hash.
  • Public Key: Freely distributed to employers, universities, and students to verify signatures.
Signing Flow (Issuance)
Certificate Data Canonical JSON SHA-256 Digest RSA Private Key + PSS Digital Signature
Verification Flow (Verification Portal)
Submitted Fields Canonical JSON RSA Public Key Verify ✓ Valid or ✗ Tampered
Why RSA-PSS? Probabilistic Signature Scheme (PSS) adds a randomized salt to each signing operation. This provides provable security bounds and defends against chosen-message attacks inherent in legacy PKCS#1 v1.5 padding.
Verification Case Analysis
Case 1: VALID Certificate
  1. Certificate ID exists in the authoritative registry.
  2. Submitted data matches stored canonical JSON string.
  3. SHA-256 hash matches the registry digest.
  4. RSA-PSS signature verifies cleanly with the public key.
  5. Revocation flag is inactive.
Case 2: TAMPERED Certificate
  1. Certificate ID exists in the trusted database.
  2. Submitted data (e.g. altered name) fails canonical JSON equality.
  3. Original signature was signed for genuine data; signature verification fails.
  4. Verdict: Rejection with clear tamper notification.
Case 3: UNKNOWN Certificate
  1. Certificate ID is absent from the authoritative registry.
  2. No trusted signature or canonical baseline exists.
  3. Verdict: NOT FOUND (unrecognized credential, not misclassified as tampered).
